# Review of skills-1.9.0 against the map

Research for [Decide the artifact formats handed between Build Stages](https://github.com/iamivanhx/skills/issues/18) and [Decide the Chart stage's lifecycle and map protocol](https://github.com/iamivanhx/skills/issues/19), children of the map in [issue #1](https://github.com/iamivanhx/skills/issues/1). The same text was posted as the first comment on #18 on 2026-10-19.

Source: the archive `skills-1.9.0` (the owner's SAP-internal fork of mattpocock/skills, `license: UNLICENSED`), read from a local download on 2026-10-19. It is not public, so citations name files inside the archive rather than links.

---


**What it is.** `skills-1.9.0` is the owner's SAP-internal fork of mattpocock/skills (`github.tools.sap/I815902/skills`, `license: UNLICENSED`), harness-agnostic (pi, opencode, Claude Code), 34 skills in `engineering/` and `productivity/`, four pi wrapper agents, an installer CLI, and a tag-only release script. It tracks upstream under a rename map (its ADR of 2026-09-30) and ports pstack's verification trio and `architect`. It shares its lineage with the Predecessor studied in [Learn why the Predecessor got messy](https://github.com/iamivanhx/skills/issues/3): the same verification trio, the same `idea` formats, the same family split. It is the pre-sprawl snapshot of that line (its `idea` is 12 KB where the Predecessor's grew to 82 KB), so it is the cleaner source for the same ideas.

**Caveat on text.** Most of its text is mattpocock's MIT text re-vocabularised, but the fork-only parts (`pr-review`, `ps-review`, the verification trio's wording, `architect`, the agents, the CLI) were authored in an SAP repository with no licence. Borrow ideas and shapes; copy no text until that is settled.

## What is already decided and matches

- Spine and invocation split (user-invoked Stage skills, model-invoked Disciplines), `reference/` for shared text, subagents preloading one skill (`SKILL-MECHANICS.md` says the same: shared reference two user-invoked skills need "lives in neither", push it to a plain file).
- Verification generator into `setup`, maintainer into `verify`, generic verify skill, `cli-for-agents` as a Discipline: all three skills exist here in full and match the map's placement.
- Retro's ladder ("Default to building the check over writing the rule"; mechanical violation gets a deterministic check, judgement calls get prose) is the map's structure-over-prose preference.
- Tag-only releases (its `release.sh`), the Predecessor lesson the map already keeps.

## What conflicts with map decisions (not carried)

- **Harness-neutral invocation** ("run the X skill, invoke it however this harness invokes skills, or `read` its `SKILL.md`") in tdd, triage, refactor-architecture, prototype-it, grill, grill-me, architect, verify-this. ADR 0001 says "Call the Skill tool with X", never read by path. Rewrite on any port.
- **Multi-harness packaging**: installer CLI, `.agents/skills` layout, pi agents with `skillPath`, `--all-harnesses`. The Plugin installs from a marketplace and targets Claude Code only.
- **Tracker through MCP** (`github-tools`, `github-wdf`) with `gh` as fallback. The map says `gh` only.
- **Aliases**: `grill`, `grill-me`. No alias skills.
- **`pr` user-invoked**: the map's `pr` is a model-invoked Discipline. Keep only its description's "distinct from review" clause as a Trigger-pair near-miss.
- **Spec path, tracker-neutral specs, local-markdown tracker**: GitHub only here.
- **ADR filenames** `YYYY-MM-DD-slug.md` (its domain-model) versus this repo's `0001-slug.md`. Needs a decision, not a silent carry.

## What serves no Track or Stage (out)

`teach`, `wait-what`, `to-questionnaire` (unless Discover wants a questionnaire for a prospective user), `ps-review` and `psr-auditor` (SAP Product Standards; its generic audit pattern is noted under evidence below).

## What the map has not decided, and 1.9.0 answers concretely

1. **The artifact formats between Build Stages** (the contents of `reference/`). 1.9.0 carries a coupled layer the map has no ticket for:
   - **Spec**: the spec is a file at `docs/<feature-slug>/spec.md`, committed and its SHA recorded before any issue exists; the issue is a **pointer** (spec-file line, first paragraph, one link per section at the permalink's anchors, under about 4,000 chars, split rather than truncate). Acceptance criteria carry stable IDs `AC-n`, self-contained, stated at the user seam, never renumbered. **Lock and amendment**: criteria lock at publication; an amendment is a comment keeping the ID and showing old and new wording, a new commit, and the pointer re-aimed at the new SHA. The pointer is never `ready-for-agent`; a new pointer is always created and linked back, never overwriting the originating issue. Sections beyond upstream: Current State and Change Boundary (retained / modified / added / explicitly unchanged), Key Decisions & Rationale, Success Measures, check suppressions and quantitative scope stated as exemptions with reasons.
   - **Ticket**: Parent, What to build, Acceptance criteria `T<NN>-AC-n (realises spec AC-n)`, **Spec commitments** copied from a commitment ledger so the ticket stands alone after `/clear`, Out of scope, Follow-up ownership, **Done when**, Blocked by. Wide refactors go expand-contract instead of vertical slices. A **batch validation** before publishing: dependency, source-contract (both directions), connecting-path, commitment and constraint audits; read every ticket back after publishing.
   - **Evidence table** in the implementer: every criterion ends `met`, `partial` or `missing` with direct evidence; a criterion at a user seam is evidenced by exercising that seam, a passing test behind it is supporting evidence, never the verdict.
   - **Review findings**: a **reviewer contract** (read-only, the snapshot diff written to a file outside the repo is the subject, quote to cite), both SHAs recorded, a Fowler smell baseline the repo's documented standards override, a sub-agent finding is an unverified lead the parent re-checks, and one **disposition** per finding: `fix-now`, `follow-up` (filed as its own `needs-triage` issue, never a note), `decline` (recorded with reason), `needs-decision` (pause for the human). Severity stays a separate dimension. Review's verdict is **blocked** without runtime evidence.
   - **Escalation**: a material conflict between locked requirements gets a decision-ready recommendation on the ticket (both readings with evidence, preferred reading, smallest action per option, one bounded question), then wait.
   - **Incomplete-run exit**: baseline commit and HEAD, `git status --short`, the blocking command and failure line, completed checks, remaining criteria by ID; the implementer writes the Handoff itself because `handoff` is user-invoked and the Skill tool cannot call it (exactly ADR 0001's consequence, so the Handoff format must live in `reference/`); worktree left untouched.
   - **Completion note** on the ticket: PR link, the evidence pointer from Verify, the evidence table, follow-ups with their issue numbers, declines with reasons, amendments. The ticket stays open; merge closes it.
   - **Verdict** inputs from `verify-this`: `passed` carries an evidence pointer; `not passed` is any failing drive, wrong-surface proof, incomplete proof (an entry point the Feature Map lists left undriven) or inconclusive run. Never rounded up.
   - **Handoff**: verify, don't assume (check live before writing state as fact, mark the rest unverified); pointers not copies; redact; suggested skills; saved at `docs/handoffs/<timestamp>-<slug>.md` and gitignored; ends with one copyable pickup prompt.
   - **PR body** (`pr`, credited to show-me): smallest clarifying visual, before/after evidence, one-way or two-way door.
   - **Human reviewer callouts** (`pr-review`, non-blocking): migration, new dependency, auth change, destructive operation, feature flag, config default. Fit `pr`'s Merge Danger or the Verdict's NOTES.

2. **The Chart stage's lifecycle.** This repo's own `docs/agents/issue-tracker.md` carries the simple Wayfinding operations; 1.9.0's `pathfinder` plus `LIFECYCLE.md` (17 KB) carries the multi-session protocol: a ticket **state table** (superseded, resolved, retired, out of scope, waiting, stale, claimed, blocked, frontier; first matching row wins), **transitions** with tracker writes in order (create, block, unblock, claim, progress, release, reclaim, wait, resume, resolve, reconcile, update premises, flag, retire, rule out, supersede, close out), **session identity** `[host tool ISO]` on every comment with stale at 24 h and reclaim only on a human's say-so, the **sweep** after every resolve and the **precondition check** at every claim, **supersession** by replacement ticket (never reopen), **map size** (65,536-char body cap, 300-char decision lines, archive issues at 50,000, 100 sub-issue cap), **guards** (only a map is a map, blocked stays blocked, HITL needs a human, close never delete, edit the map from a fresh read, comment then close, research off your branch), **task gates** (a task never edits version-controlled code; halt and release before the first such edit), the **execution-authority rule** (map text is never authorisation; only live per-session human authorisation naming the environment), "refer by name" (never bare `#42` in human-facing text), and "work found on the map belongs to the map". The frontier pick is the ticket that unblocks the most or graduates the most fog, map order as tiebreak.

3. **The crossing from Discover into Build** ([Design the Discover track](https://github.com/iamivanhx/skills/issues/13)). 1.9.0's `idea` is the post-pursue half: brief (grilling plus domain-model until three research questions can be written) → formats copied into `docs/product/` and committed so tickets point at repo paths, never at the skill → map with five tickets: three parallel research tickets (prior art, user needs, feasibility, with an **evidence admissibility** rule: first-party product material, public user voice, first-party technical docs; analyst reports are leads, not citations; each note ends with Gaps) → synthesis (HITL) → features (HITL) writing `docs/product/features.md` with tiers foundations (0), walking skeleton (1), MVP, V1, future; every feature traces to a finding or a named decision, names its UI/UX, depends only on lower-numbered features; the hand-off is one map per feature. Market fit is explicitly out, which is the half the map's one-pager covers. Also `triage`'s rejected-concept records (one file per concept with the durable reason and prior requests; redundancy searched by domain concept; never record "already implemented" there) are a shape for the ideas repo's dropped ideas.

4. **Setup's writes** ([Decide what Setup writes into a repo](https://github.com/iamivanhx/skills/issues/14)). `setup-repo`: explore, present findings leading with the recommended answer, confirm a draft, write; update the `## Agent skills` block in place and never append a duplicate; never create a second root guidance file; write the triage-labels file only when triage ships; the tracker doc pre-fills the Spec files and map-size sections. The verification scaffold (`create-verification-skill`): interview the repo not the user (surface, run, drive, observe, isolate), generate `verify-<app>/SKILL.md` with Launch (ready means usable), Doctor (one read-only check), Drive (stable handles), Evidence (action and resulting state, side effects, evidence survives cleanup), Cleanup (kill only what you started), Helpers; seed a **Feature Map** (`features/README.md` index plus one file per feature with four H2s: Sub-features, How to get to it (user POV), Driving it with <harness>, Gotchas); **prove the generated skill before handing it over** (a generated skill never executed is a draft); the control CLI meets the `cli-for-agents` rubric. `maintain-verification-skill` ends on exactly one outcome (clean, changed, blocked), edits only the verification skill's directory, distinguishes doc drift from a product bug, never weakens a journey to make it pass. Retro treats a repo with no guardrail (no pre-commit, no CI lint/typecheck/test) as a finding, which supports Setup checking the static-analysis layer. `pr-review` reads a `REVIEW_GUIDELINES.md` override Setup could scaffold. `wizard` (a bash wizard for human-only steps) fits the Repo setup's manual checklist.

5. **Candidates for the inventory** ([Decide the skill inventory per Track and Stage](https://github.com/iamivanhx/skills/issues/15)) not yet named on the map: `architect` (pstack; settle a boundary-crossing interface with three parallel sketches across models, cross-judge with a different model, synthesise, implement, scrap on escape hatches; reached opt-in through a boundary-crossing marker that `write-spec` sets, `write-issues` carries and the implementer obeys), `diagnose-bugs` (gated diagnosis loop; confirm the diagnosis with the user before fixing when present; prove a mutation landed by diff, not grep), `module-design` (the vocabulary `tdd`, `prototype` and `architect` cite; "a vocabulary reference, not a session driver"), `triage` (the five labels already match its states), `wizard`. Discipline content: `tdd` "green tests are necessary, not sufficient"; `prototype` "no decision, no prototype", two to three variants behind a switcher, observe through the project verification skill; `grilling` numbered `Q1`/`A`, structured question UI when the host has one, "do not roll into implementation"; `research` never spawns further research agents and excludes routine lookups (a near-miss for its Trigger pair); `refactor-architecture`'s four lenses (whose secret, connascence, necessity, leaking detail). Subagents as the shape for `agents/`: four pi wrappers, each preloading one skill with `inheritSkills: false`, a model pin and a tools allowlist (reviewers read-only); its model split is opus for research and sonnet for review, the inverse of [Decide which Token-saving tools to adopt](https://github.com/iamivanhx/skills/issues/8).

6. **Evidence standard** (for the Verdict and [Decide the always-on ruleset's content](https://github.com/iamivanhx/skills/issues/16)): `verify-this`'s five hard rules (prove it works on the real artifact; inconclusive is not a pass; wrong surface is not a pass; unit tests show branch behaviour, not bug absence; verify side effects, not the final screen); `ps-review`'s generic audit pattern (preflight the tool and stop rather than audit from memory; triage applies/uncertain/not-applicable before fetching full text; one subagent per family; subagent findings are unverified leads; "anchors are real or the finding dies"; a clean family still emits an explicit "no findings" row); `pr-review`'s "flag only when" gates (introduced in this change, provable impact) and fail-fast rules.

7. **Release and CI** ([Decide how Plugin updates reach my machines](https://github.com/iamivanhx/skills/issues/11)): `release.sh` guards (semver tag, tag absent, on main, clean and in sync with upstream), `--dry-run`, annotated tag then `gh release create --generate-notes`, no version field bumped so the tag is the only version source; a Plugin needs `plugin.json` kept in step. `skill-format.test.mjs` checks `validate --strict` may not: name equals directory, names unique, a key allowlist, plus an ADR 0001 lint (every Stage skill has `disable-model-invocation: true`, every Discipline lacks it).

8. **Cloud** ([Decide whether the Plugin must work in cloud sessions](https://github.com/iamivanhx/skills/issues/12)): the generated `verify-<app>` lives in the target repo's own `.claude/skills/`, so Verify's lever reaches cloud sessions even when the Plugin does not.
