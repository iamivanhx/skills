# How agents can work ready-for-agent issues unattended, locally

Research for [issue #21](https://github.com/iamivanhx/skills/issues/21), child of the map [#1](https://github.com/iamivanhx/skills/issues/1). Feeds [Decide how Implement runs unattended](https://github.com/iamivanhx/skills/issues/22).

- **Primary sources**: the Claude Code docs at <https://code.claude.com/docs/en/> and the Agent SDK pages under it, read as raw Markdown via the [llms.txt index](https://code.claude.com/docs/llms.txt) on 2026-10-19; the [`gh` manual](https://cli.github.com/manual/) (gh 2.102.0); [GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue); the [anthropics/claude-code](https://github.com/anthropics/claude-code) repo.
- **Version caveat**: the docs track Claude Code v2.1.30x (v2.1.303 installed here). Minimum versions are given where a feature needs one.
- **Scope**: local runs on macOS, Linux and Windows (Git Bash) only, per [#12](https://github.com/iamivanhx/skills/issues/12). Cloud gets one paragraph (section 4).
- Vocabulary follows `GLOSSARY.md`: **Plugin**, **Repo setup**, **Workflow**, **Stage**, **Stage skill**, **Discipline**.

## Answer in brief

- **Nothing in Claude Code watches a GitHub label locally.** Every local route needs a trigger you supply: a script you run, an OS timer, a Desktop local scheduled task, or a long-lived session with `/loop`. The docs cover none of cron, launchd or Task Scheduler.
- **Two drivers fit "one ticket per fresh session"**: a script that runs `claude -p` once per issue (sequential, structured result, exit codes), and a script that dispatches `claude --bg` once per issue (parallel, auto-isolated in a worktree, visible and attachable in `claude agents`). Both load the user's installed Plugin, `~/.claude`, hooks and CLAUDE.md, as long as you don't pass `--bare`.
- **`--bare` is the trap**: it skips plugins, hooks, skills and CLAUDE.md, never reads OAuth, so it needs an API key. It "will become the default for `-p` in a future release".
- **Permissions**: `--permission-mode auto --permission-prompts none` is the documented unattended combination. Auto mode lets the agent push branches and open PRs, but blocks merging an unapproved PR, approving its own PR, and force pushes. That already matches the Workflow's human merge gate. Pushing to the default branch is allowed by default, so add a deny rule.
- **Claiming** is plain `gh issue edit` (assignee `@me` and/or a label flip). GitHub offers no atomic claim, so you avoid races by running one dispatcher per repo.
- **Cost and limits**: runs draw on the subscription. `-p` runs, background sessions and workflows in `-p` don't wait out a usage limit, so the driver has to back off and retry. N parallel sessions use quota about N times as fast.
- **Ranked recommendation** (section 7): a Plugin `bin/` dispatcher that runs `claude -p` per issue, with `claude --bg` per issue as the parallel mode. A Desktop local scheduled task or an OS timer can be the trigger. `/loop`, `/goal`, workflows, `/batch` and the Agent SDK don't fit as the queue driver.

## 1. Headless drivers

### 1.1 Comparison

| Driver | Fresh context per issue | Loads installed Plugin, `~/.claude`, hooks | Survives terminal close / reboot | Windows | Fit |
| :- | :- | :- | :- | :- | :- |
| Script loop over `claude -p` | Yes, one process per issue | Yes unless `--bare` ([headless](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)) | Lives as long as the script; needs a trigger | Yes | **Best sequential driver** |
| Script dispatching `claude --bg` | Yes, one background session per issue | Starts "the way a new `claude` session in that directory would" ([agent-view](https://code.claude.com/docs/en/agent-view#permission-mode)) | Survives terminal close and sleep, stops on shutdown ([agent-view#limitations](https://code.claude.com/docs/en/agent-view#limitations)) | Yes (supervisor recovery mentions `taskkill`, [agent-view](https://code.claude.com/docs/en/agent-view#troubleshooting)) | **Best parallel driver** |
| `/loop` in a session | No: one conversation accumulates | Inherits the session | Session-scoped; recurring tasks expire after 7 days; a self-paced loop isn't restored on resume ([scheduled-tasks](https://code.claude.com/docs/en/scheduled-tasks#limitations)) | Yes | Trigger at most |
| `/goal` | No: same session keeps going | Inherits the session | Session-scoped | Yes | Inside one ticket, not across the queue |
| Dynamic workflow (`workflows/*.js`) | Each `agent()` is a fresh subagent, not a session | Runs inside the session | Resumable within the session ([workflows](https://code.claude.com/docs/en/workflows#resume-after-a-pause)) | Yes | Fan-out within a Stage, not the queue |
| Agent SDK (TS/Python) | Yes, one `query()` per issue | Same as the CLI when `settingSources` is omitted ([claude-code-features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)); plugins only by local path ([sdk plugins](https://code.claude.com/docs/en/agent-sdk/plugins)) | As long as your process runs | Yes | Overkill; docs steer to API-key billing |
| Desktop local scheduled task | Yes, a fresh session per fire ([desktop-scheduled-tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks#how-scheduled-tasks-run)) | Desktop reads the same config files as the CLI ([desktop](https://code.claude.com/docs/en/desktop)) | Persistent; app must be open and the machine awake | Yes; Linux app is beta, Debian-based only ([desktop-linux](https://code.claude.com/docs/en/desktop-linux)) | Good trigger, GUI-configured |
| `/batch` | Worktree subagents | Session | Session | Yes | One large change, plan needs approval ([commands](https://code.claude.com/docs/en/commands)) |

### 1.2 `claude -p` driven by a script

- **Shape**: `claude -p "<prompt>"` runs non-interactively. It exits 0 on success and non-zero on failure. A failure inside the run, such as missing auth, prints as the result on stdout ([headless#basic-usage](https://code.claude.com/docs/en/headless#basic-usage)).
- **Stage skills work in `-p`**: "User-invoked skills and custom commands work. Include `/skill-name` in the prompt string" ([headless#create-a-commit](https://code.claude.com/docs/en/headless#create-a-commit)). So a user-invoked `implement` Stage skill (ADR 0001) can be the prompt. A plugin subagent can also be the main agent: `claude --agent my-plugin:implementer` ([sub-agents](https://code.claude.com/docs/en/sub-agents#invoke-subagents-explicitly)).
- **What loads**: without `--bare`, `-p` "discovers and loads them as an interactive session would, including anything configured in the working directory or `~/.claude`" (hooks, skills, subagents, installed plugins, MCP, auto memory, CLAUDE.md) ([headless](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)). Monitors don't load, because they are interactive-only ([components#monitors](https://code.claude.com/docs/en/plugins/components#monitors)).
- **Plugin install race**: in `-p`, "plugins install in the background and may not be available on the first turn" unless `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1` ([env-vars](https://code.claude.com/docs/en/env-vars)). The `system/init` event lists `plugins` and `plugin_errors`, so a driver can fail fast when the Plugin didn't load ([headless#fail-ci-when-a-plugin-or-mcp-server-doesnt-load](https://code.claude.com/docs/en/headless#fail-ci-when-a-plugin-or-mcp-server-doesnt-load)).
- **Structured outcome**: `--output-format json` returns `result`, `session_id` and `total_cost_usd`. `--json-schema` adds a validated `structured_output`, such as `{status, pr_url}` ([headless#get-structured-output](https://code.claude.com/docs/en/headless#get-structured-output)). Error subtypes include `error_max_turns`, `error_during_execution` and `error_max_budget_usd` ([typescript SDKResultMessage](https://code.claude.com/docs/en/agent-sdk/typescript)).
- **Bounds**: `--max-turns` and `--max-budget-usd` are print-mode only. The budget cap is a client-side estimate and "spend can pass the cap" ([cli-reference](https://code.claude.com/docs/en/cli-reference#cli-flags)).
- **Stopping**: the run ends when the turn finishes. It waits for background subagents and workflows, and stops other idle background work after 10 minutes ([headless#background-tasks-at-exit](https://code.claude.com/docs/en/headless#background-tasks-at-exit)). SIGTERM exits 143 and runs `SessionEnd` hooks ([headless#stop-a-run-with-sigterm](https://code.claude.com/docs/en/headless#stop-a-run-with-sigterm)).
- **Trust**: `-p` shows no workspace-trust dialog and runs project hooks and `.mcp.json` "even in a folder you've never trusted" ([headless](https://code.claude.com/docs/en/headless#start-faster-with-bare-mode)).

### 1.3 `claude --bg` background sessions (agent view, research preview)

- `claude --bg --name <n> "<prompt>"` starts a full interactive session hosted by a supervisor and returns at once. `--bg` can't combine with `-p`. In a script it fails with `Workspace not trusted` unless the folder was trusted once ([agent-view#dispatch-an-agent-from-your-shell](https://code.claude.com/docs/en/agent-view#dispatch-an-agent-from-your-shell)).
- **Isolation built in**: before editing, the session moves into a worktree under `.claude/worktrees/`. It is then told to commit, push the branch, and open a draft PR "when the task calls for it". It never pushes to `main`/`master`, force-pushes or merges ([agent-view#how-file-edits-are-isolated](https://code.claude.com/docs/en/agent-view#how-file-edits-are-isolated)).
- **Reading state from a script**: poll `claude agents --json --all`. `state` is one of `working`, `blocked` (needs you), `done`, `failed` or `stopped`, and `waitingFor` names the prompt ([agent-view#read-session-state-from-a-script](https://code.claude.com/docs/en/agent-view#read-session-state-from-a-script)). `claude logs`, `claude stop`, `claude respawn` and `claude rm` manage sessions.
- **Lifecycle**: the supervisor starts on the first `--bg` or `claude agents`. It restarts crashed sessions and stops idle ones after about an hour, keeping the conversation ([agent-view#the-supervisor-process](https://code.claude.com/docs/en/agent-view#the-supervisor-process)). Sessions don't survive shutdown, and nothing restarts the supervisor at boot.
- **Plugins**: `claude agents` passes `--plugin-dir`, `--settings` and `--setting-sources` through to dispatched sessions ([agent-view#settings-plugins-and-mcp-servers](https://code.claude.com/docs/en/agent-view#settings-plugins-and-mcp-servers)).
- **Permissions**: a `--bg` session takes the mode a new session in that directory would. `auto` and `bypassPermissions` as `defaultMode` take effect only from `~/.claude/settings.json`, managed settings or `--settings` ([agent-view#permission-mode](https://code.claude.com/docs/en/agent-view#permission-mode)). Unlike `-p`, a blocked session waits visibly for you to attach.

### 1.4 `/loop`, `/goal`, workflows, `/batch`, Agent SDK, Desktop tasks

- **`/loop`**: runs a prompt on an interval while the session is open. Tasks fire only while Claude Code is running and idle, there's no catch-up, and recurring tasks expire after 7 days ([scheduled-tasks](https://code.claude.com/docs/en/scheduled-tasks#limitations)). Backgrounding carries `/loop` into a background session. **A scheduled fire only runs skills Claude may invoke itself; `disable-model-invocation: true` skills "reach Claude as plain text instead of executing"** ([scheduled-tasks#run-a-prompt-repeatedly-with-loop](https://code.claude.com/docs/en/scheduled-tasks#run-a-prompt-repeatedly-with-loop)). Under ADR 0001 Stage skills are user-invoked, so `/loop /implement` would not run the Stage skill.
- **`/goal`**: keeps one session working until a model judges a condition met. It works in `-p`, and the docs list "Working through a labeled issue backlog until the queue is empty" as a use ([goal](https://code.claude.com/docs/en/goal)). But it is one conversation, which breaks "one ticket per fresh session". It fits inside a ticket ("until tests pass").
- **Dynamic workflows**: a JS script orchestrates up to 16 concurrent agents by default, 1,000 per run, with "No mid-run user input" ([workflows#behavior-and-limits](https://code.claude.com/docs/en/workflows#behavior-and-limits)). In `-p` no approval prompt is shown, so the Workflow tool needs a `Workflow` allow rule, auto mode, bypass, a hook or a host ([workflows#approve-the-plan-before-it-runs](https://code.claude.com/docs/en/workflows#approve-the-plan-before-it-runs)). The `ultracode` keyword doesn't trigger from a `-p` prompt or a scheduled-task prompt. A Plugin can ship one in `workflows/` ([workflows#distribute-a-workflow-in-a-plugin](https://code.claude.com/docs/en/workflows#distribute-a-workflow-in-a-plugin)). In `-p` a run doesn't pause at a usage limit; the affected agents fail ([workflows#when-a-run-hits-your-usage-limit](https://code.claude.com/docs/en/workflows#when-a-run-hits-your-usage-limit)).
- **`/batch`**: splits one large change into 5 to 30 worktree subagents after you approve a plan ([commands](https://code.claude.com/docs/en/commands)). It solves a different problem.
- **Agent SDK**: a library that runs the Claude Code binary. Omitting `settingSources` loads user, project and local settings, CLAUDE.md, skills, agents and hooks ([claude-code-features](https://code.claude.com/docs/en/agent-sdk/claude-code-features)). Plugins load only as `{type: "local", path}`. For CLI-installed plugins, "Check `~/.claude/plugins/`" ([sdk plugins](https://code.claude.com/docs/en/agent-sdk/plugins)). The quickstart uses an API key and says Anthropic does not allow third-party developers to offer claude.ai login for SDK products ([sdk quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart)). It needs Node or Python. Anything it adds over `claude -p --output-format stream-json` (callbacks, `canUseTool`) isn't needed for this queue.
- **Desktop local scheduled tasks**: the app starts a fresh session per fire, with a per-task permission mode, model, folder and optional worktree. The schedule runs only while the app is open and the machine awake, with one catch-up run on wake. A run is skipped while the previous one is still running ([desktop-scheduled-tasks](https://code.claude.com/docs/en/desktop-scheduled-tasks)). The prompt lives in `~/.claude/scheduled-tasks/<name>/SKILL.md`, but schedule, folder and model are set only through the app. In Manual mode a run stalls on a prompt until you answer.
- **Not a driver**: the `ralph-wiggum` plugin in anthropics/claude-code loops one prompt in one session through a Stop hook ([README](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)). It gives the same session, not a fresh one.

### 1.5 Worktree isolation

- `claude -p -w <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`, from the remote default branch by default (`worktree.baseRef: "fresh"`). `-p` skips the trust check ([worktrees](https://code.claude.com/docs/en/worktrees#start-claude-in-a-worktree)).
- **`-p` doesn't clean up its worktrees**, and the lock stays until a later stale-lock sweep. Remove them with `git worktree remove` ([worktrees#clean-up-worktrees](https://code.claude.com/docs/en/worktrees#clean-up-worktrees)). The periodic sweep removes subagent and background-session worktrees older than `cleanupPeriodDays` unless they hold unpushed work.
- While isolated, Claude Code blocks edits, command cwd and git redirects into the main checkout, for the session and its subagents ([worktrees#how-claude-code-enforces-isolation](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation)).
- A worktree is a fresh checkout. Dependencies must be installed there, and gitignored files like `.env` need a `.worktreeinclude` ([worktrees](https://code.claude.com/docs/en/worktrees#set-up-the-worktree-environment)). Project-scope plugins and untracked `.claude/skills` read through to the main checkout ([worktrees#what-worktrees-share-with-the-main-checkout](https://code.claude.com/docs/en/worktrees#what-worktrees-share-with-the-main-checkout)).
- `gh issue develop <n> --checkout --worktree <path>` creates a branch linked to the issue in a worktree ([gh issue develop](https://cli.github.com/manual/gh_issue_develop)). Claude Code's own `-w` doesn't link the branch to the issue.

### 1.6 Where the driver should live

- **Plugin `bin/`** puts executables on the Bash tool's `PATH` while the Plugin is enabled ([components#executables](https://code.claude.com/docs/en/plugins/components#executables)). That is inside sessions only, not on your login shell's `PATH` for cron. An OS timer would call it by its install path under `~/.claude/plugins/` (layout per [sdk plugins](https://code.claude.com/docs/en/agent-sdk/plugins); exact cache path isn't documented as stable).
- **Plugin skill** (`implement`) holds the per-ticket procedure. The driver only claims an issue and launches `/<plugin>:implement <n>`. This keeps the one-home rule from ADR 0001.
- **Repo setup** owns anything outside the Plugin's reach: `~/.claude/settings.json` (`defaultMode`, deny rules, `skipDangerousModePermissionPrompt` if ever needed), the OS timer, and `CLAUDE_CODE_OAUTH_TOKEN`/`GH_TOKEN` for timer-launched runs. A plugin's `settings.json` honours only `agent` and `subagentStatusLine` ([components#default-settings](https://code.claude.com/docs/en/plugins/components#default-settings)).
- **Product repo**: nothing. The driver runs from the Plugin against any repo with `ready-for-agent` issues, which keeps the "never a dependency" rule.

## 2. Queue mechanics

- **Find work**: `gh issue list --label ready-for-agent --search "no:assignee" --json number,title,blockedBy` ([gh issue list](https://cli.github.com/manual/gh_issue_list), which lists both `no:assignee` and the `blockedBy` field). gh 2.102 also writes these relationships (`--add-blocked-by`), so the driver can skip a ticket with an open blocker ([gh issue edit](https://cli.github.com/manual/gh_issue_edit)).
- **Claim**: `gh issue edit <n> --add-assignee @me` and/or a label flip (`--remove-label ready-for-agent --add-label <in-progress>`) ([gh issue edit](https://cli.github.com/manual/gh_issue_edit)). The docs are silent on atomicity, and GitHub offers no compare-and-set on labels or assignees. Assume races are possible and run one dispatcher per repo. The five default triage labels have no "in progress" state, so whether to add one is for #22.
- **One issue per fresh context**: one `claude -p` process or one `claude --bg` session per issue gives this by construction. `--no-session-persistence` stops transcripts being saved ([cli-reference](https://code.claude.com/docs/en/cli-reference#cli-flags)). Keep persistence on so a failed run can be `--resume`d by `session_id`.
- **Open the PR and stop**: the skill ends with `gh pr create` and `Closes #<n>` in the body. Closing keywords only take effect for PRs into the default branch ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue), [gh pr create](https://cli.github.com/manual/gh_pr_create)). Auto mode allows pushing to any branch of the repo and "creating a pull request that matches your request" ([permission-modes](https://code.claude.com/docs/en/permission-modes#what-the-classifier-blocks-by-default)). `--json-schema` returns the PR URL to the driver.
- **Failure handling**: branch on the exit code and `subtype`. On failure, comment on the issue, unassign it or flip the label back, and move on. `-p` runs and background sessions don't offer the usage-limit wait ([interactive-mode#wait-for-a-usage-limit-to-reset](https://code.claude.com/docs/en/interactive-mode#wait-for-a-usage-limit-to-reset)), so a limit hit fails the run and the driver must stop for the window. API errors are retried internally and reported as `system/api_retry` events ([headless#handle-api-retries](https://code.claude.com/docs/en/headless#handle-api-retries)).
- **Parallelism**: one `--bg` session per issue isolates itself in a worktree. `claude -p -w` does the same for scripts. Running ten agents "uses quota roughly ten times as fast" ([agent-view#limitations](https://code.claude.com/docs/en/agent-view#limitations)).
- **`gh` auth**: `gh auth login` stores the token in the system credential store and falls back to a plain-text file ([gh auth login](https://cli.github.com/manual/gh_auth_login)). `GH_TOKEN` overrides stored credentials, and `GH_PROMPT_DISABLED` stops prompts ([gh environment](https://cli.github.com/manual/gh_help_environment)). The docs are silent on keychain access from cron or launchd, so a timer-launched driver should export `GH_TOKEN`.
- **Claude auth**: `claude setup-token` mints a one-year subscription token for `CLAUDE_CODE_OAUTH_TOKEN`, meant "for CI pipelines and scripts". It can only make model requests, so no claude.ai connectors and no Remote Control ([authentication#generate-a-long-lived-token](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token)). Synced (`@synced`) plugins don't load under it, but marketplace plugins do ([loading#synced-plugins](https://code.claude.com/docs/en/plugins/loading#synced-plugins)). On macOS the login lives in the Keychain, with a file fallback when it's locked ([authentication](https://code.claude.com/docs/en/authentication)). A background session "that outlives the login stops making progress" until you sign in again.
- **Hand-off to Verify**: a fresh `claude -p "/<plugin>:verify <pr>"` after Implement makes Verify a separate session, so a non-author. Auto mode's default block on "Merging a pull request no human has approved, approving Claude's own pull request, or disabling CI checks" ([permission-modes](https://code.claude.com/docs/en/permission-modes#what-the-classifier-blocks-by-default)) backs the human merge gate.

## 3. Running without prompts

- `--permission-mode auto --permission-prompts none` is the documented unattended setup. The classifier reviews each action, anything that would prompt is denied, and Claude is told not to retry. It needs v2.1.259 or later ([headless#turn-off-permission-prompts-in-unattended-runs](https://code.claude.com/docs/en/headless#turn-off-permission-prompts-in-unattended-runs)). In `-p`, repeated classifier blocks don't stop the run; the action is skipped ([permission-modes#repeated-block-thresholds](https://code.claude.com/docs/en/permission-modes#repeated-block-thresholds)).
- Auto mode is available on all plans with Opus/Sonnet 4.6+ ([permission-modes](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode)). Classifier checks run server-side at no charge where available, and "Pro, Max, and Team plans never show" the notice about billed classifier requests ([auto-mode-classifier-billing](https://code.claude.com/docs/en/auto-mode-classifier-billing)). The "no API proxies" rule matters here, because a proxy forces billed classifier calls.
- **Defaults to override**: pushing to the default branch is allowed by default. `permissions.deny` rules still block push commands as written ([permission-modes](https://code.claude.com/docs/en/permission-modes#what-the-classifier-blocks-by-default)), and branch protection is the hard guarantee.
- **Boundaries stated in a prompt are not durable**: they can be lost to compaction ("For a hard guarantee, add a deny rule").
- **bypassPermissions** is for "containers and VMs only" ([permission-modes](https://code.claude.com/docs/en/permission-modes#skip-all-checks-with-bypasspermissions-mode)). Auto mode also blocks "Launching an autonomous agent loop that runs without human approval or a sandbox, such as one started with `--dangerously-skip-permissions`". A Claude session that runs the driver could be refused if the driver uses bypass.
- **Windows**: the Bash sandbox doesn't run on native Windows ([sandboxing](https://code.claude.com/docs/en/sandboxing)), so auto mode and deny rules are the only guard there. Git for Windows provides Git Bash for the Bash tool ([setup](https://code.claude.com/docs/en/setup)).

## 4. Out of scope: cloud and the GitHub Action

Routines run in the cloud on a schedule, an API call, or GitHub events such as `pull_request.opened`. They don't need your machine on ([routines](https://code.claude.com/docs/en/routines)). Cloud sessions don't load user-installed plugins or `~/.claude` ([cloud-environments](https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup)). The Claude Code GitHub Action runs on GitHub runners, triggers on issue and PR events or `@claude`, and accepts a subscription `CLAUDE_CODE_OAUTH_TOKEN`. It can install a plugin through `plugin_marketplaces`/`plugins` inputs, but a committed workflow that names the Plugin would make the product repo depend on it ([github-actions](https://code.claude.com/docs/en/github-actions)). Compared with these, a local driver lacks event triggers (it must poll) and can't run while the machine is off or asleep.

## 5. Where the docs are silent

- Running `claude` from cron, launchd, systemd timers or Windows Task Scheduler: no page mentions them, including how the macOS Keychain behaves for a launchd job.
- Whether `-p` will keep loading installed plugins once `--bare` becomes the default, and whether an opt-out flag will exist.
- Atomic claiming of a GitHub issue (GitHub Docs and `gh` say nothing about concurrent assignee or label edits).
- Whether a Desktop local scheduled task's instructions can invoke a `disable-model-invocation: true` skill (the `/loop` rule is documented, the Desktop one isn't).
- Whether the Agent SDK may use a personal claude.ai login for your own unattended scripts. The docs only forbid third-party products offering it.
- Whether auto mode treats a session running `claude -p --permission-mode auto` from Bash as "launching an autonomous agent loop".
- A stable path for a marketplace-installed plugin's `bin/` outside a session.

## 6. Surprises for other tickets

1. **`--bare` will become the `-p` default** and drops plugins, hooks, CLAUDE.md and OAuth. That affects eval harnesses ([#9](https://github.com/iamivanhx/skills/issues/9)) and any headless Plugin use. Check `system/init.plugins` in every headless run.
2. **Stage skills can't be fired by `/loop`** (user-invoked skills reach Claude as plain text). That bears on ADR 0001 and on any "keep going" automation.
3. **`claude --bg` already does the Implement tail**: worktree, commit, push and draft PR, never merge or push to main. Implement can lean on it rather than restate it.
4. **Auto mode's defaults encode the merge gate** (no merging unapproved PRs, no self-approval). But they allow pushing to `main`, so the Repo setup should add a deny rule and Setup should turn on branch protection.
5. **No sandbox on native Windows**: unattended runs there rely on auto mode alone.
6. **Usage limits end unattended runs** instead of waiting, and parallel sessions multiply quota use. No cost cap exists on a subscription beyond the client-side `--max-budget-usd` estimate.
7. **`claude setup-token` tokens drop synced plugins and claude.ai connectors.** The Plugin is marketplace-installed per [#11](https://github.com/iamivanhx/skills/issues/11), so it is unaffected.
8. **gh 2.102 has native blocked-by relationships** (`--add-blocked-by`), which can order a Spec's child tickets without a convention of our own.

## 7. Recommendation: local drivers ranked for this Workflow

1. **A Plugin `bin/` dispatcher around `claude -p`, one issue per process.** List `ready-for-agent` with no assignee and not blocked, claim, then run `CLAUDE_CODE_SYNC_PLUGIN_INSTALL=1 claude -p -w issue-<n> --permission-mode auto --permission-prompts none --output-format json --json-schema <outcome> "/<plugin>:implement <n>"`. Read the result, unclaim on failure, stop on a usage limit, clean the worktree. Fresh context by construction, structured outcome, plain bash (Git Bash on Windows), subscription auth. Pass the Plugin explicitly if `--bare` ever becomes the default.
2. **The same dispatcher in parallel mode with `claude --bg`, one session per issue.** You get built-in worktree isolation and the commit/push/draft-PR tail, plus `claude agents` to watch and attach when a run is `blocked`. The driver reads outcomes from `claude agents --json --all` and from GitHub. It is still a research preview, and quota use scales with the number of sessions.
3. **Triggers, not drivers**: a Desktop local scheduled task (fresh session per fire, GUI-configured, app open and awake) or an OS timer from the Repo setup (undocumented by Anthropic, needs `CLAUDE_CODE_OAUTH_TOKEN` and `GH_TOKEN`). Starting the dispatcher by hand is the simplest trigger.
4. **Not as the queue driver**: `/loop` (expires, can't fire Stage skills, one context), `/goal` (one context; use it inside a ticket), dynamic workflows (fan-out within a Stage; agents fail at usage limits in `-p`), `/batch` (one change), and the Agent SDK (API-key billing per its docs, extra runtime, nothing `-p` lacks here).
